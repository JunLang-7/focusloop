# FocusLoop 专注体验改造调研

调研日期：2026-09-18

外部参考（Tiimo）的核实记录见 [focus-redesign-facts.md](./focus-redesign-facts.md)。

## 结论先行

FocusLoop 现在的「专注页」本质上是会话状态监控页，不是专注执行环境。它很完整地告诉
用户系统状态、总用时、总体完成数、开始时间和全部后续任务，却没有把「现在只做哪一小步」
变成唯一视觉中心。

Tiimo 值得借鉴的不是紫色、沙漏插图或大圆环，而是三个交互原则：

1. **时间可见**：时间是一段能看见、能调整的空间，不只是 `0:00` 数字。
2. **下一步唯一**：专注中只出现一个任务和一组最必要控制。
3. **控制可逆**：暂停、加一分钟、换小一步、提前完成都不带惩罚感。

对 demo 阶段最合适的方向，是把当前页改成「专注执行台」：保留 FocusLoop 独有的微任务、
状态判断和中断续接能力，但让这些能力只在需要时出现。第一版不需要重做整个信息架构，也
不需要先实现复杂 AI。

## 当前体验诊断

### 1. 首屏回答错了问题

当前第一张卡片依次展示：状态、会话已用时、总进度、开始时间。它回答的是「这次会话发生了
什么」，而专注中的首要问题应该是：

- 我现在只做什么？
- 还要坚持多久？
- 卡住或被打断后如何回到原位？

因此当前任务虽然有强调色，仍然只是第二张卡片；用户需要先穿过一层分析信息才能行动。

### 2. 同一屏存在过多注意力竞争

专注时仍然同时显示：

- 完整侧栏与设置；
- 今日统计和状态标签；
- 四个会话指标；
- 当前任务；
- 全部后续任务及每个任务的开始按钮；
- 代理建议浮层；
- demo 模拟器。

这些元素单独都有理由，但一起出现时等于把选择权重新丢给了用户。尤其「后续计划」在视觉上
占据页面最大面积，会持续提醒用户还有很多没做完。

### 3. 已经借到了 Tiimo 的“计划可视化”，但没有借到“专注模式”

`session-plan.ts` 已明确采用 Tiimo 式的时间几何，把任务时长映射为连续区块。这一改动适合
计划阶段，却不适合正在执行的阶段。计划需要看全局，专注需要收窄视野。当前页面把二者叠在
同一层级，导致「看起来更像 Tiimo」，但「用起来还不是专注」。

### 4. FocusLoop 最强的能力没有成为主舞台

FocusLoop 真正独特的不是计时器，而是：

- 把学习材料拆成 3–8 分钟微任务；
- 识别启动困难、困惑、过载、分心和中断；
- 保存认知检查点；
- 回来后恢复到具体的思考位置；
- 以低频、可解释的方式给出干预。

现在这些能力分散在状态标签、浮动 Agent 卡和恢复弹窗里。用户看到的是基础设施，不是一个
连贯的「进入—专注—卡住—回来—继续」流程。

## 从 Tiimo 应该借什么

### 应该借

- 大尺度、低信息密度的专注画布；
- 图形化时间进度和明确剩余时间；
- 开始前可调整时长，开始后可 `+1 分钟`；
- 暂停是正常状态，不是失败；
- 可选的氛围声音层，但不抢任务的主层级；
- 专注期间只保留极少控制；
- 通过任务拆分降低启动门槛。

### 不应该照搬

- 不复制 Tiimo 的紫色渐变、图标、插画或品牌语言；
- 不把 FocusLoop 退化成通用番茄钟；
- 不用装饰性的「疗愈感」替代真正的任务引导；
- 不让音频、连胜或奖励系统压过「认知续接」这个核心差异；
- 不把桌面端强行做成放大的手机 UI。

## 推荐方案：专注执行台

### 状态 A：准备开始

目标是解决启动困难，而不是展示统计。

主画面只保留：

- 当前微任务标题；
- 一句具体指令；
- 按任务预计时长生成的视觉时间环；
- 主按钮「先做 3 分钟」或「开始 3 分钟」；
- 次级入口「换一个任务」。

如果任务预计 8 分钟，不必强迫用户一次承诺 8 分钟。默认可以先承诺 3 分钟，并在开始后通过
`+1 分钟` 或「继续完成」延长。这比单纯显示预计时长更贴合启动困难场景。

### 状态 B：专注中

进入沉浸模式后：

- 收起侧栏，只保留一个很弱的退出/展开入口；
- 隐藏今日统计、总进度、后续任务和设置；
- 当前任务成为唯一标题；
- 中央显示视觉倒计时与剩余时间；
- 指令缩成一句可执行动作；
- 底部只保留「暂停」「+1 分钟」「卡住了」「完成」；
- demo 模拟器只在开发模式通过快捷键或折叠抽屉出现。

视觉上应避免仪表盘感。不要用四张指标卡或多色状态灯；重点是一个大的时间对象和一条动作指令。

### 状态 C：暂停或卡住

暂停后不要直接弹出复杂 Agent 面板。把当前画布转成三个清晰选择：

- 「继续」；
- 「把这一步再缩小」；
- 「休息 3 分钟」。

这三个动作可直接映射已有的 `MICRO_START / SIMPLIFY / BREAK` 干预语义。Agent 的解释放在
次级文本中，不抢主动作。

### 状态 D：完成微任务

任务完成后短暂确认一次，然后只预览下一个任务：

- 「完成了」；
- 下一步标题与预计时长；
- 「继续下一步」和「先收尾」两个选择。

不要立刻重新铺开完整任务列表。完整计划应放在准备阶段或右侧抽屉中。

### 状态 E：被打断后返回

这是 FocusLoop 应该明显超越 Tiimo 的地方。

现有恢复卡应从通用弹窗改成同一专注画布里的「续接状态」：

- 你刚才在做什么；
- 已经做到哪里；
- 仍卡在哪里；
- 现在只需要做的下一小步；
- 一个大按钮「从这里继续」。

详细检查点、完成项和未解决项可以折叠查看。默认不让用户重新理解一遍整场会话。

## 三档改造路径

### 方案 1：Tiimo-lite 视觉重排（最快）

预计工作量：1–2 天。

- 重排 `focus.page.ts`，把当前任务和视觉计时放到首屏；
- 专注中通过 CSS 状态类收起侧栏、统计卡和后续计划；
- 用现有 `estimatedMinutes` 画一个 SVG/CSS 时间环；
- 后续任务移入「查看计划」抽屉；
- Agent 浮层改成当前画布内的安静提示；
- demo 模拟器折叠。

优点：最快看到变化，绝大部分是 renderer 层改动。

限制：当前共享 `LearningSession` 没有向 renderer 暴露 `taskStartedAt`，因此第一版若要真实倒计时，
需要补一个很小的只读字段，或从最近的 `TASK_STARTED` 事件推导。

### 方案 2：FocusLoop 原生认知续接（推荐）

预计工作量：3–5 天。

包含方案 1，并增加：

- 明确的准备 / 专注 / 暂停 / 续接 / 完成五态；
- 「先做 3 分钟」微承诺；
- 「卡住了」后在原位提供提示、拆小或休息，而不是浮动面板；
- 恢复卡整合进专注画布；
- 任务完成后只展示下一步；
- 增加任务级计时和暂停事件。

这是最能体现产品差异的一档：借 Tiimo 的安静执行方式，但核心叙事仍然是 FocusLoop 的
「认知不断线」。

### 方案 3：沉浸式 Focus Companion

预计工作量：5–8 天。

包含方案 2，并增加：

- 可选的 Lo-Fi / 白噪声层；
- 系统级专注模式或勿扰提示；
- 迷你悬浮窗显示当前任务与剩余时间；
- 浏览器扩展只提供弱提醒和一键返回；
- 更完整的 task-level session 统计。

这档适合验证长期产品形态，不适合作为第一轮 demo 改造。

## 建议本轮 demo 的范围

采用「方案 1 的外壳 + 方案 2 的续接核心」。具体只做以下内容：

1. 准备态：当前微任务 + 视觉时间环 + 「先做 3 分钟」。
2. 专注态：收起所有非当前任务信息，保留倒计时、暂停、卡住、完成。
3. 卡住态：原位展示「提示 / 拆小 / 休息」，复用已有 intervention policy。
4. 续接态：把现有 Resume Card 改为专注画布内的单一步骤恢复。
5. 计划抽屉：保留现在的比例时间块，但默认关闭。
6. 开发模拟器：折叠到右下角「Demo controls」。

暂时不做：音频、连胜、跨设备小组件、复杂奖励动画、全新课程系统。

可能需要的小型领域改动：

- 增加 `TASK_PAUSED / TASK_RESUMED`，如果本轮需要真实暂停而不是纯 UI 暂停；

- 不修改 intervention policy 的优先级，先只改变它的呈现位置。

## 成功标准

第一次看到新专注页时，用户应在 2 秒内回答：

- 我现在做什么；
- 还剩多久；
- 卡住怎么办；
- 做完点哪里。

同时，专注状态下首屏不应出现：完整任务队列、四项统计、主题/语言设置、今日分析或持续可见的
demo 模拟器。

## 本轮落地情况（issue #27）

本分支落地了「方案 1 的外壳 + 方案 2 的续接核心」中可以在 renderer 内完成的部分。

已实现：

- 准备态：只显示下一个微任务与主按钮「先做 3 分钟」（`DEFAULT_FOCUS_MINUTES`），不再先显示会话状态卡；
- 专注态：当前任务 + 一句指令 + 视觉时间环 + `暂停 / +1 分钟 / 卡住了 / 完成`；时间环由
  `core/focus-timer.ts` 的 `progress` 驱动；
- 暂停与超时：时间环冻结，状态写在环内（`paused` / `time is up`），不弹面板；
- 完成态：只确认一次，然后只预览下一步，不再铺开剩余列表；
- 计划抽屉：复用 #24 的比例时间块，默认折叠，摘要里保留剩余总时长。开关状态由 renderer 持有
  （`core/plan-visibility.ts`），因此 Escape、点击别处、以及开始或完成一步都会收起它；做成
  `<details>` 时只有摘要能关掉它，且专注时那张卡片会盖在任务上（#71）；
- 专注中的外壳：侧栏收成 64px 图标栏，品牌文字、今日统计与设置隐藏。这一层是纯 CSS
  （`styles.css` 的 focus mode 段用 `:has()` 判断 `data-phase`），没有改动 `app.component.ts`。

尚未实现，留给后续 issue：

- 「卡住了」在画布内给出「提示 / 拆小 / 休息」三选一：现在仍只派发 `HELP_REQUESTED`，由既有
  intervention policy 与浮层面板呈现；
- 恢复卡改成画布内的「续接状态」：现在仍是模态对话框；
- 领域层暴露 task-level `taskStartedAt`，以及 `TASK_PAUSED / TASK_RESUMED`：本轮的承诺是
  renderer 本地状态，离开页面即失效，不写入事件日志；
- demo 模拟器折叠为右下角抽屉或快捷键：模拟器仍常驻底部；
- 方案 3 的全部内容：氛围音频、迷你悬浮窗、系统级专注模式。

## 验证方法

时间环的正确性没有靠肉眼看截图判断。逐像素测量圆弧（半径、角度覆盖）发现
`vector-effect: non-scaling-stroke` 会让浏览器按屏幕单位解释 `stroke-dasharray`，而路径长度仍按用户
单位计算，于是虚线比周长多出 1.38 倍：表现是圆弧恒为约 101°、沿着环滑动，而不是随进度增长。
移除该声明后，同一测量在 0% / 17% / 34% 进度上分别得到 5° / 64° / 125°，即从 12 点开始顺时针
线性增长。
